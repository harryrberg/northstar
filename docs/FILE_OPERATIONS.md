# Opening-menu file operations

The reference is the WordStar Professional 4.00 `WS.EXE` identified in the [compatibility profile](COMPATIBILITY_PROFILE.md). The isolated run `C:/Projects/rea/investigations/wordstar/runtime-openstar-files-01` contains the input manifest, ordered actions, screenshots and final files. It used a copy of the program disk, not the source upload.

With the opening menu visible, O asked for `Document to be copied?` and then `Name a document to hold the new copy.` Typing `CHAPTER1.DOC` and `COPY.DOC` created a 128-byte copy with the same SHA-256 value, `48744756e61617249c8490edab8ff339e375ba74e010538bdf41a0c0799e8bbf`. E asked for `Document to be renamed?` and then `What do you want its new name to be?` Changing `COPY.DOC` to `RENAMED.DOC` removed the old directory name and retained those bytes. Y asked for `Document to be erased?` and then `Are you sure (Y/N)?` N retained the file; a second Y sequence removed it. These are observations for one ordinary file on the logged DOS drive. The run did not establish wildcard behavior, existing-target handling, read-only attributes, other drives, or error text.

OpenStar implements O, E and Y for one regular file at a time. Relative names use the logged directory; absolute paths are accepted. A copy creates a new file without replacing an existing target. Rename uses a hard link followed by removal of the old name, so it is limited to one volume and cannot replace an existing target. If old-name removal fails, both names remain and the error identifies the new name. Y requires an explicit confirmation. Symlinks and directories are rejected. These are safety and platform choices, not claims about WordStar's handling of the unobserved cases. None of these operations changes an open editor buffer.

The synthetic desktop tests cover source and target prompts, copied bytes, no-replace behavior, rename, N cancellation and Y deletion. They do not exercise another operating system or prove matching pixel placement in the Windows app.
