# Fidelity contract

Fidelity is a testable relationship to an identified original and declared behavior. It is not inferred from key bindings, screenshots, function counts, or the amount of pseudocode exported.

Every scenario must record:

1. Scenario identity and claimed behavior.
2. Reference executable identity, relevant configuration, and initial document bytes.
3. Initial cursor, editor modes, and other result-affecting state; unknowns remain explicit.
4. Ordered semantic commands and, where relevant, physical key events and timing.
5. Expected document bytes, cursor/modes, and relevant display or output observations.
6. Source evidence paths and identities; distinguish static findings from actual execution.
7. Compared fields, permitted differences, unexplained differences, and unexamined scope.

Synthetic fixtures must have their construction recorded. Archived observations can establish a case only when their initial conditions and resulting facts support it. A fresh original-program replay is a separate activity from verifying retained evidence.

The core owns semantic state. Adapters may translate platform keys, input method composition, coordinates, and display metrics, but must not reinterpret WordStar command behavior independently.

Keep original file bytes and unknown controls recoverable. Explicitly distinguish legacy compatibility behavior from Unicode, autosave/recovery, modern output, and other extensions. Never silently claim legacy compatibility for lossy conversion.

A milestone report lists passing scenarios, failures, unknowns, and platforms actually exercised. No percentage of full WordStar compatibility is reported without a defined, justified behavioral denominator.
