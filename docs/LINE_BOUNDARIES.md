# Ctrl-Q S and Ctrl-Q D line boundaries

The reference is WordStar Professional 4.00 `WS.EXE`, SHA-256 `535235e6a392d344948d065a5553798e6119b2a0c25ccbaca2221b6b4860904d`. Two isolated DOSBox runs, `runtime-openstar-quick-line-01` and `runtime-openstar-quick-line-02` under `C:/Projects/rea/investigations/wordstar`, used a synthetic 128-byte `SEED.DOC` containing `ONE TWO\r\nTHREE FOUR\r\n` and trailing 1A padding. Each run retains the seed construction, ordered actions, screenshots, final carrier and executable manifest. The seed SHA-256 is `67cda60077217c67dc76e7ae786a57396707824785400b7e67f841b65360c806`.

From line 1 column 5, Ctrl-Q S reached column 1. Ctrl-Q D then reached column 8, immediately after `ONE TWO`. On line 2, Ctrl-Q D reached column 11 after `THREE FOUR`, and Ctrl-Q S returned to column 1. On the empty final line, Ctrl-Q D stayed at column 1. Five `navline-*` CLI scenarios compare the derived byte offsets and unchanged carrier bytes with the retained screens. A desktop workflow also sends the actual prefix keys and checks the same results. `tools/verify-local-evidence.py` verified the local source identities.

The measured profile is ordinary one-byte ASCII text on physical lines with hard CRLF breaks. The core uses the same boundary for soft spaces and soft breaks, but these Ctrl-Q cases have not been compared in DOS. It refuses unsupported control cells and dot-command lines rather than guessing. Page-marked breaks, horizontal scrolling, and non-document mode are also unqualified. UTF-8 documents have a separate input policy; Ctrl-Q S/D currently applies only to the legacy editor.
